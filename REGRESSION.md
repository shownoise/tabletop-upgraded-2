## 3. Why five rows all read round 1 with identical values

`ScoringPanel` renders `scoring.outcomes` (see `outcome-round.ts::computeRoundOutcome`), which produces one row per `scenario.rounds` entry, keyed by `r.number`. If the panel shows five rows all labelled `1` **with identical per-axis values `-1.0 / -0.0 / -1.0 / -1.0`**, that vector matches `NO_DECISION_FALLBACK_VECTOR = { CONT: -1, FOR: 0, BC: -1, JUR: -1, VER: 0, KOS: 0 }` exactly. Normalising that with equal weights gives −0.25, which produces `points = round(100 · (−0.25 + 1) / 2) = 37`. Five rounds × 37 = **185**. Every number the user sees is generated by the engine when it sees zero submissions.

The "all rows labelled round 1" part is a labelling defect *on top of* the "no data" defect. But the labelling is a symptom: even if labelling were correct, all five rows would still show identical fallback vectors. Fix the pipeline first; the label defect resolves itself once real data flows.

## 4. The break in the decision → scoring pipeline (this is Phase 1 root cause)

Two paths write decision points into the scoring scenario spec (`lib/scoring/graph-adapter.ts::graphToScenarioSpec`):

- **DecisionNode**: `decisionPoint.id = node.id` (line 75); each option has its own unique id (line 82 via `optionFromDecision(o)` at line 264).
- **RoleAction (on RoundNode)**: `decisionPoint.id = a.id` and its single option also has `id: a.id` (line 274-289).

The event written when a participant submits (`lib/scoring/graph-adapter.ts::submittedDecisionToEvent`, line 339-351):
```ts
{
  decisionPointId: d.actionId,   // whatever is on SubmittedDecision.actionId
  optionId: d.actionId,           // same
  ...
}
```

For a RoleAction submission that works — both ids are the same `a.id`. For a **DecisionNode option** submission, `d.actionId` is the **option id** (session-store.ts:1376: `dd.options.find(o => o.id === input.actionId)`), never the node id. But the scoring engine looks up decision points by their node id at `outcome-round.ts:35`: `submissionsById.get(dp.id)`. The event's `decisionPointId` (an option id) will never equal the spec's `dp.id` (a node id). **The submission is silently dropped.**

Consequence: if a scenario uses `DecisionNode` (which the current default `OPERATIE POLDER-STORM` example does), *no* decision ever registers, every round falls back to `NO_DECISION_FALLBACK_VECTOR`, and the panel shows the identical 37/185 pattern.

This is the answer to "why is the scoring pipeline disconnected". It is one bug, not many. Everything the user described downstream is what a healthy engine renders when it receives no data.

## Root cause, one sentence

The previous refactor built the correct new panel and the correct new engine input path, but did not delete the old panel. The old panel calls a scoring engine that receives no data because the DecisionNode → SubmittedDecision → scoring-event id conversion drops the containing node id, so every submission is silently unmatched.

## Consequence for this pass

Deleting `ScoringPanel` alone is not sufficient — the underlying disconnect (event → decision point id mismatch) would still bite `RevealPanel` the moment the session reached REVIEW with a DecisionNode-driven scenario. **Both fixes must land**: delete the shadow panel *and* repair `submittedDecisionToEvent` so DecisionNode submissions map back to their containing node id.
